# proposals 目录规则（候选设计输入，非实现）

本目录存放从 `docs/`、`pdfs/`、导师意见、评审记录和对话中分析出来的**待定（draft / unconfirmed）**材料：候选设计、结构映射、验收集、待核结论和开放问题。它不是稳定设计，不是实现说明，也不是需求。

## 状态口径

- 本目录所有文件默认 `draft / unconfirmed`，除非文件头明确写出用户已确认的版本与范围。
- 每个文件头必须写：状态、来源、日期、用途、不构成什么。
- 引用原始材料时保留文件身份，并区分“原文”与“归纳/分析”。扫描件转录属于分析产物，不是原文，不得当引文使用。
- 结论与实测事实分开写：可复核的数字（包内节点/字段/关系数等）标注实测来源；推测和设计判断标注为草案。

## 硬性禁止

读取本目录时，不得：

1. 把这里的内容当作当前实现、既有能力或已验收产物的证据；
2. 把这里的内容当作 `md/` 稳定设计或 `tasks/overall/` 最终需求的替代或等价物；
3. 把这里的内容当作思维层设计的用户确认，或据此开始编码、制作执行性原型、写实现测试、修改生产代码，或派单给其他 AI 执行；
4. 据此修改 `src/`、`schemas/`、`md/`、`tasks/`、`docs/`、`pdfs/`、知识包、语义注册表或运行产物；
5. 把这里的字段名、关系词表、评分公式、阈值、聚类参数、Agent/Skill 划分写进 Schema、注册表、数据包或发行物；
6. 把这里的医学解释、候选名称、聚类结果或书中的理论模型当作知识事实、诊断结论、医学审核结论或已采纳方法；
7. 因本目录提到某个 Skill、Agent、字段或关系，就认定它已存在或已登记。

违反上述任一条，都等于把待定材料当成实现依据。

## 允许的使用方式

- 只读引用、讨论、批注、拆分、推翻、标记待核；
- 基于本目录起草设计稿、评审意见或派单说明的**草案**，但草案仍须留在本目录或经确认后写回权威文件；
- 用本目录的验收集做离线结构检查；检查结果只能说明结构与可审计性，不得宣称医学正确或能力已实现。

## 升格路径

只有用户明确确认某个提案的版本与范围后，才允许：

1. 写入 `md/`（稳定设计）或 `tasks/overall/`（能力口径）；
2. 同步 `tasks/STATE.md`、`tasks/HANDOFF.md`、`tasks/CURRENT.md`；
3. 按 `tasks/overall/规则与变更策略.md` 的“思维层实现前的用户设计确认门”开始实现或派单。

未确认的提案留在本目录。不得以“继续推进”“路线图已有”“其他任务已验收”“只是原型/测试”替代确认。

## 与相邻目录的区别

| 目录 | 内容 | 权威性 |
|---|---|---|
| `docs/` | 导师提供的原始材料 | 只读来源，不修改 |
| `md/` | 稳定产品与技术设计 | 已确认设计 |
| `tasks/overall/` | 最终需求与能力口径 | 权威需求 |
| `tasks/evidence/` | 当前任务的非敏感证据摘要 | 任务证据 |
| `proposals/` | 待定候选设计、映射与分析 | 无权威性 |
