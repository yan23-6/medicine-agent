# 项目周报记录规则

本目录用于保存面向导师的项目阶段周报。周报通常每周整理一次，核心是比较“本周状态”与“上一次周报状态”，说明新增、修改、确认、推迟和仍未解决的事项。

## 1. 更新权限

- 禁止自动创建或更新周报。
- 只有用户明确提出“更新 log”“生成本周周报”或含义等同的指令时，AI 才能修改本目录中的周报产物。
- 普通开发、文档修改、代码提交或阶段总结不能被视为更新周报的授权。
- 用户只要求建立或修改周报规则时，不得顺带生成周报。
- 已生成的历史周报原则上只读；如需更正，必须保留更正说明，不得静默改写历史。

## 2. 文件格式

- 周报产物必须使用 Markdown。
- 文件名使用 `YYYY-MM-DD-项目周报.md`，日期采用周报生成日或用户指定日期。
- 本文件只规定统计和报告方式，不属于某一周的周报。

## 3. 统计方法

生成周报前按以下顺序核对：

1. 找到本目录日期最近的一份历史周报，作为上周基线；没有历史周报时，明确标记为“首次基线”。
2. 检查自上次周报以来的 Git 提交、工作区变更、文档版本和新增产物；Git 不可用时，使用文件内容、修改时间和用户提供的信息，并注明统计边界。
3. 只统计已经实际完成或已经明确确认的变化，不把讨论、设想和计划写成完成项。
4. 将变化分成新增、调整、确认、验证、遗留问题和下一步，不以文件数量代替实际进展。
5. 对需求或架构变化，说明“原来是什么、现在是什么、为什么变化、影响哪些模块”。
6. 对没有变化的部分保持简洁，不重复大段项目背景。
7. `docs` 中的导师原始资料可以只读参考，但不得改写；新增参考文件本身不自动算作项目成果，只有已经吸收到正式设计、实现或验证中的内容才计入进度。

## 4. 周报结构

每份周报使用以下结构：

```markdown
# 项目周报 YYYY-MM-DD

## 本周结论

用一段话说明本周相对上次周报的主要变化和当前阶段。

## 相比上周的变化

- 新增：
- 调整：
- 已确认：
- 已验证：

## 当前产物

列出本周新增或实质变化的设计、数据、代码、实验或报告产物。

## 未完成与风险

只列仍影响下一阶段的事项，区分未开始、进行中、受阻和待确认。

## 下周计划

列出少量可验证的下一步，不承诺未经确认的时间或结果。

## 统计范围

记录对比基线、截止时间、使用的证据以及任何统计限制。
```

## 5. 表述要求

- 面向导师，语言简洁、客观、可核对。
- 首先报告结论和增量，再报告过程。
- 严格区分“已设计、已实现、已测试、已审核、已发布”。
- 不夸大医学价值、临床效果、系统完成度或论文创新。
- 对尚未确定的事项使用“候选、待验证、待确认”，不能写成正式结论。
- 若本周没有实质变化，应如实说明，不为形成周报而制造进展。
