# 规则与变更策略

## 1. 权威顺序

1. 用户当前明确要求；
2. `AGENTS.md`；
3. 实际代码、Schema、测试与运行产物；
4. `tasks/STATE.md` 与 `tasks/CURRENT.md`；
5. `tasks/overall/` 与 `md/` 稳定设计；
6. `tasks/ROADMAP.md`；
7. `tasks/archive/`、`log/` 和 Git 历史。

历史文件只能证明当时发生过什么，不能证明当前文件或能力仍存在。

## 2. 需求变更

### 数据层与思维层的AI执行口径

按“主体业务逻辑分开、公共基础设施共用”理解和实施。数据层侧重材料生产、包管理、校验、基础查询/索引和复核；思维层侧重病例驱动的检索选择、联想扩展、候选推演、追问和停止决策。基础查询返回事实与证据，思维策略通过接口使用；模型抽取和来源推理片段保存仍可属于数据生产。共享模型、Schema、语义注册表、存储、Runner、Skill注册与通用工具均允许，不要求严格隔离或复制公共实现。

AI设计、派单、编码、评审和验收都须标明改动属于数据业务、思维业务或公共能力，跨层时说明调用方向与输入输出；不要把辨证策略塞进基础查询/包生产，也不要因共用基础设施而擅自创建隔离重构任务。思维改动保持数据功能、接口与旧包兼容；共享组件按实际影响回归，不以任意模块损坏后的启动存活作为本项目默认验收门。总体边界见md/02-整体技术架构.md，思维层实现确认门继续有效。

需求变化必须同步：

- 稳定产品/技术设计 `md/`；
- 最终需求和能力表 `tasks/overall/`；
- 当前任务、下一任务和路线图；
- 受影响的接口、Schema、测试和说明。

名称或职责变化也要同步输入、输出、依赖、调用关系、交付和验收，并说明旧名称映射。

## 3. 实现声明

### 思维层实现前的用户设计确认门

开始新增、替换或实质扩展思维层实现前，必须停止该部分执行，向用户明确询问“是否已确认本次思维层设计，可以按该版本和范围开始实现？”，收到明确确认后才能继续。思维层包括病例驱动的检索策略、联想扩展、候选推演、评分、追问、剪枝、停止条件及相关Agent编排；不以任务名、阶段编号或“小样/测试/重构”为由绕过。

确认前允许整理设计、只读检查和影响分析；不得先写相关实现、执行性原型或实现测试，也不得先派给DeepSeek或其他AI执行。将确认的设计文件/版本、范围和用户确认记录写入CURRENT/HANDOFF；设计实质变化或超出已确认范围时重新确认。泛指“继续推进”、已有路线图、旧规则原型及数据层任务授权均不能替代本次确认。未获确认只暂停依赖该确认的工作，可继续独立的数据层CURRENT任务。

当前用户尚未确认新的思维层设计。现有基础查询、来源绑定、包校验、复核及其独立工程验证不因此停止；一旦包含上述思维策略，必须先触发确认门。

只有同时满足以下条件才能写“已实现/已验证”：

- 实际产物存在；
- 前置成立；
- 验收命令真实运行；
- 失败和未覆盖项明确记录；
- 软件通过与医学验收没有混写。

## 4. 数据与版本

数据包结构默认维持现有兼容基线；推理链、编排、查询、索引或界面调整先在包外完成。只有现有结构不能表达必要事实或必须修复完整性问题，且兼容扩展无法满足时，才提出结构变更，并同步必要性依据、版本、旧包兼容、迁移/回滚与验收。不得因项目尚未终稿而随意改包，不把结构调整转成整书重蒸馏。

- 旧包优先兼容读取，不为索引变化整体返工；
- 只有原证据或关键语义缺失才局部迁移/重提；
- 新公开结构必须版本化并生成 Schema；
- 来源节点和原文身份不可被派生视图覆盖；
- 破坏性迁移必须有备份、回滚和明确授权。
- 后补包不阻塞可独立验收的工程任务；新增资料处理先核对来源指纹、有效成果和待补范围，不能因包缺失整书重提。自主补齐不包括伪造医学评审或自行授权外发/权重发布。

## 5. 外部模型和敏感资料

- 每次真实资料外发必须有明确材料范围和目的地授权；
- 历史许可不自动扩展到新页、新服务或新任务；
- 本地配置只由运行时读取，不进入输出；
- 原始 PDF、患者资料和运行产物不提交；
- FakeModel 和自制夹具只能证明软件行为。

## 6. 文档维护

- 稳定设计不写日期进度；
- 当前状态只写 `STATE.md`；
- 当前执行细节只写 `CURRENT.md`；
- 历史验收归档，不与现行入口平铺；
- 自动生成文档只从唯一来源重建；
- `docs/` 原始资料和 `log/` 周报遵守各自目录规则。
