# 规则与变更策略

## 1. 权威顺序

1. 用户当前明确要求；
2. `AGENTS.md`；
3. 实际代码、Schema、测试与运行产物；
4. `tasks/STATE.md` 与 `tasks/CURRENT.md`；
5. `tasks/overall/` 与 `md/` 稳定设计；
6. `tasks/ROADMAP.md`；
7. `tasks/archive/`、`log/` 和 Git 历史。

历史文件只能证明当时发生过什么，不能证明当前文件或能力仍存在。

## 2. 需求变更

需求变化必须同步：

- 稳定产品/技术设计 `md/`；
- 最终需求和能力表 `tasks/overall/`；
- 当前任务、下一任务和路线图；
- 受影响的接口、Schema、测试和说明。

名称或职责变化也要同步输入、输出、依赖、调用关系、交付和验收，并说明旧名称映射。

## 3. 实现声明

只有同时满足以下条件才能写“已实现/已验证”：

- 实际产物存在；
- 前置成立；
- 验收命令真实运行；
- 失败和未覆盖项明确记录；
- 软件通过与医学验收没有混写。

## 4. 数据与版本

- 旧包优先兼容读取，不为索引变化整体返工；
- 只有原证据或关键语义缺失才局部迁移/重提；
- 新公开结构必须版本化并生成 Schema；
- 来源节点和原文身份不可被派生视图覆盖；
- 破坏性迁移必须有备份、回滚和明确授权。
- 后补包不阻塞可独立验收的工程任务；新增资料处理先核对来源指纹、有效成果和待补范围，不能因包缺失整书重提。自主补齐不包括伪造医学评审或自行授权外发/权重发布。

## 5. 外部模型和敏感资料

- 每次真实资料外发必须有明确材料范围和目的地授权；
- 历史许可不自动扩展到新页、新服务或新任务；
- 本地配置只由运行时读取，不进入输出；
- 原始 PDF、患者资料和运行产物不提交；
- FakeModel 和自制夹具只能证明软件行为。

## 6. 文档维护

- 稳定设计不写日期进度；
- 当前状态只写 `STATE.md`；
- 当前执行细节只写 `CURRENT.md`；
- 历史验收归档，不与现行入口平铺；
- 自动生成文档只从唯一来源重建；
- `docs/` 原始资料和 `log/` 周报遵守各自目录规则。
