# 规则与变更策略

## 1. 决策等级

- `fixed`：已经形成稳定契约，变更需要同步修改设计、迁移和回归测试；
- `provisional`：当前推荐方案，进入实现前必须验证；
- `deferred`：缺少真实数据或前置能力，暂不决定；
- `rejected`：已经否决，除非出现新证据不得重新采用。

## 2. 需求与任务同步

- 每推进一个可核验步骤，同步更新 `tasks/STATE.md` 与 `tasks/HANDOFF.md`，记录当前任务、已验证结果、下一动作及授权/阻塞。此为持续规则，不仅用于交接收尾。
- 用户每次调整需求，即使幅度很小，都要检查相关稳定设计与任务链并实际更新受影响文档，保证项目逻辑统一完整；不能只依靠聊天记忆。
- Agent/Skill 职责变化须同步角色、内部工具、调用与数据流、输入输出、依赖和验收，记录旧称对应关系，避免竞争定义。
- 推进前先检查除 docs 参考材料、log 周报外全部 Markdown 与现有设计/功能的一致性；历史记录标明时点，生成文件从唯一来源维护。修正后再编码。修改后检查一致性、文档引用与前置产物，再用极简中文告诉用户当前需要提供文件还是开始构建；已有授权不重复询问。

- `md` 的稳定设计改变后，必须检查终极需求、当前阶段和未来阶段；
- 未来任务不提前锁定具体算法、版本和阈值；
- 当前任务必须足够详细，可由没有聊天上下文的 AI 执行；
- 当前任务不得调用 `STATE.md` 中标记为不存在的能力；
- 如果实现发现设计不成立，先形成设计变更建议，不能在代码中静默改变协议。

## 3. 阶段门

每个阶段只有在以下条件同时成立时完成：

- 规定产物存在；
- 自动检查通过；
- 人工或专家验收完成；
- 未解决风险已记录；
- `STATE.md` 已更新；
- 下一阶段的前置条件已经真实满足。

## 4. 可迁移性

原始资料与版本化代码分离：`pdfs/` 可本地读取分析，Git 仅保留 `.gitkeep`；不得提交其中任何 PDF 原件，也不能复制改名后绕过。任务快照、OCR、预览和实验包保存在被忽略的 artifacts，原件不进入测试或发行物。此为用户已确认的来源管理规则，不表示禁止本地分析。

仓库被复制到其他项目或环境后，AI 应通过根目录 `AGENTS.md` 和 `tasks` 恢复项目状态。任何运行依赖、模型或外部服务都必须在任务中显式声明，不得依赖原聊天或机器上的隐式配置。
