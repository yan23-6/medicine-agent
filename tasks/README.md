# 项目任务系统

本目录把长期设计转换为可执行任务。它解决“项目最终要做什么”和“现在下一步做什么”之间的断层。

## 1. 信息层级

优先级从高到低为：

1. `md/README.md` 与 `md/14`、`md/15`：稳定设计基线；
2. `tasks/overall`：终极能力范围、技术边界、Agent 与 Skill 总表；
3. `tasks/STATE.md`：当前真实状态；
4. 当前阶段的 `README.md`：阶段目标与阶段门；
5. 当前阶段的 `CURRENT_TASK.md`：当前唯一正式任务；
6. 当前阶段的 `NEXT_TASK.md`：下一任务预告；
7. `FUTURE.md`：本阶段后续思路，不可直接执行。

若内容冲突，先停止执行并把“解决冲突”作为当前任务，不得自行选择方便的版本。

## 2. 任务选择规则

```text
读取 STATE
  → 找到当前阶段
  → 验证 CURRENT_TASK 的前置产物
  ├─ 前置缺失：补齐最早缺失能力
  ├─ 存在阻塞决策：先完成决策任务
  ├─ 可以执行：返回当前任务
  └─ 已验收：更新状态后进入 NEXT_TASK
```

每次只详细执行一个任务。返回任务时，应同时给出下一任务预告和后续阶段方向，但不得提前实现未来任务。

## 3. 任务文档最低要求

正式任务必须包含：

- 背景和历史原因；
- 当前真实能力，明确哪些能力不存在；
- 任务目标和用户价值；
- 前置条件；
- 本次必须确定的设计与技术选择；
- 功能和非功能需求；
- 输入、输出和接口；
- 数据、证据、版本和错误要求；
- 产物清单；
- 验收标准和检查方法；
- 明确不在本次处理的内容；
- 可调整项和固定项；
- 完成后允许进入的下一任务。

## 4. 状态词

- `idea`：远期思路；
- `draft`：需求草案，尚未进入执行；
- `ready`：前置条件满足，可以执行；
- `in_progress`：正在执行；
- `blocked`：缺少明确决策或外部条件；
- `review`：产物已形成，等待验收；
- `done`：产物存在且验收通过；
- `superseded`：被新任务或新决策替代。

未来阶段默认使用 `idea` 或 `draft`。不得仅因为文档写得详细就把状态提升为 `ready`。

## 5. 变更原则

- 稳定契约变化时，先更新 `md` 设计基线，再更新任务；
- 具体技术、算法和物理格式可以在阶段开始前重新评审；
- 已完成任务不静默改写，需求变化通过新任务或替代说明处理；
- 任务完成后更新 `STATE.md`，但不自动生成 `log` 周报。
