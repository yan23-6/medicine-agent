# LadybugDB、热插拔与跨环境使用

## 1. 已确认的选型

平台默认采用 LadybugDB 作为嵌入式图数据引擎。它随平台运行，不要求用户安装 Neo4j、PostgreSQL、Docker、Java 或单独维护数据库服务。

选择 LadybugDB 的主要理由是：

- 数据库直接嵌入应用进程，符合复制或安装平台后即可使用的目标；
- 支持磁盘持久化、属性图和 Cypher，适合病机节点、关系和路径查询；
- 支持全文检索与向量检索，可覆盖原文搜索、语义召回和图扩展；
- 可以针对不同操作系统随发行物提供所需运行组件；
- 延续了原项目选择 Kuzu 时看重的轻量、嵌入式和无独立服务特点；
- 为未来几十个科目、每科数十本材料的增长保留了磁盘化图存储能力。

LadybugDB 官方说明其不需要独立服务器，可由程序直接打开磁盘数据库：[LadybugDB 入门文档](https://docs.ladybugdb.com/get-started/)。Kuzu 原仓库已于 2025 年归档，因此本项目不再将其作为新的长期基础：[Kuzu 官方仓库](https://github.com/kuzudb/kuzu)。

本选型仍需通过真实中医数据和放大数据集进行性能验证。当前确认的是默认方向，不预先承诺未经测试的最终容量上限。

## 2. 知识包与运行数据库的区别

知识包负责交换和交付，LadybugDB 负责运行时联合查询。

知识包由不同人员分别蒸馏形成，可以来自教材、论文、医家经验、医案或其他允许材料。每个包保留独立来源、版本、科目、能力、质量和许可信息，不要求制作者拥有同一个数据库。

所有包共同服从平台唯一的知识包协议说明书。单包只携带机器可读的最小自描述和实际知识数据，不携带另一套使用说明。平台已经内置统一解释、查询和校验规则，因此新增普通兼容包无需修改 Skill、提示词或核心代码。

LadybugDB 工作库由使用平台在本地维护。知识包被放入约定位置后，平台自动发现、校验并纳入工作库。查询时面向已启用包的联合图进行，而不是让智能体逐个读取文件。

## 3. LadybugDB 中保存什么

LadybugDB 在逻辑上保存：

- 知识节点及其来源身份；
- 病因、病位、病性、病机、证候、治法等关系；
- 三层病机结构及跨层映射；
- 医家经验和医案诊次之间的联系；
- 标准病例、临床观察、诊次状态和多诊次轨迹；
- 可审计的中医病机路径、西医临床路径、证明图和安全门状态；
- 必要的原文或 OCR 证据文本及来源位置；
- 数据包身份、版本、启用状态和作用域；
- 全文和向量检索所需信息；
- 自动判断、人工评审、冲突和修订状态。

原文证据作为可以被多个知识节点和关系共同引用的独立知识对象保存，避免在每个节点中反复复制相同大段文本。大型 PDF、页面图片和其他二进制原件可以由平台文件存储管理，图中保留可靠关联。

当前阶段不确定具体节点表、关系表、字段和文件格式。

## 4. 多数据包放在一起后的处理流程

当不同人员把同一科目的兼容数据包放到约定位置后，平台应自动完成：

1. 发现新增或变化的数据包；
2. 读取包的身份、统一协议版本、科目、资料类型配置、版本和能力自描述；
3. 按项目级统一说明书校验结构、完整性、兼容性、许可和质量状态；
4. 防止同一包或同一版本重复纳入；
5. 在受控状态下将包内容纳入该科目的 LadybugDB 工作库；
6. 为来源知识保留独立命名空间和包身份；
7. 更新全文检索、向量检索和图查询所需索引；
8. 生成与通用病机、其他专家包和医案包的候选映射；
9. 将低置信、冲突和高风险映射交给复核；
10. 完成后把数据包切换为已启用状态。

从使用者角度，操作仍然是“复制数据包并等待平台显示可用”。首次纳入大型数据包和建立索引可能耗时，因此即插即用表示无需人工配置，不表示大数据可以零时间完成处理。

“只复制数据包”成立的兼容边界是：平台已经携带对应版本的统一说明书，数据包自描述完整，未使用平台不支持的主版本或受控扩展，并通过完整性、安全和许可校验。不兼容包进入隔离区并给出迁移原因，不能由智能体临时猜测其结构。

## 5. 联合查询方式

同一科目的多个已启用数据包进入共同查询范围后，系统能够在一次任务中同时检索教材解释、论文断言、名医经验和病例证据。

默认联合查询必须：

- 保留每条结果来自哪个包、哪份材料和哪个版本；
- 通过通用病机概念汇聚相关来源，但不覆盖来源节点；
- 允许同名异义、异名同义和部分相关；
- 并列展示不同医家、论文和教材的冲突；
- 支持按科目、包、材料类型、医家、年代和审核状态过滤；
- 支持从通用病机进入医家经验和具体医案，也支持反向回溯；
- 停用某个包后立即停止使用其内容和跨包映射。

不采用“每个知识包就是一个独立 LadybugDB，然后让一个查询同时遍历所有数据库”的默认模式。LadybugDB 当前对外部 Ladybug 数据库的附加主要用于只读切换，并不适合作为大量独立包的实时跨库图遍历基础：[LadybugDB 外部数据库文档](https://docs.ladybugdb.com/extensions/attach/lbug/)。因此知识包保持独立交付，运行时由平台统一纳入工作库。

## 6. 安装、停用、升级和卸载

- 新包先校验和暂存，完成索引与必要映射后才启用；
- 处理失败的包进入隔离状态，不影响已经可用的包；
- 包文件暂时不可见时先停用，不立即破坏性删除；
- 升级时先准备新版本，验证完成后再切换默认版本；
- 旧版本按策略保留，以支持回滚和结果复现；
- 确认卸载后，撤销本包内容、索引贡献和跨包映射；
- 任一操作都不得静默修改其他来源包的事实。

## 7. 依赖与发行要求

“少依赖、即插即用”是正式非功能需求：

- LadybugDB 运行库随对应操作系统的发行物提供；
- 全文、向量等必要扩展随发行物提供并锁定兼容版本；
- 默认运行不得要求临时联网安装数据库组件；
- 不同操作系统和处理器架构可以使用不同发行物；
- 开发者可使用简化初始化流程，普通用户应使用解压或安装即可运行的发行物；
- 大代码仓库只需保存框架、说明和小型测试数据，大型知识包通过独立渠道获取。

“拉取代码后自动可用”仍受智能体环境的安全和插件安装规则约束。合理目标是开发环境经过一次受控初始化，或普通用户安装一次适配包后即可使用，而不是绕过宿主环境授权。

## 8. 不同智能体环境的支持

核心平台保持独立运行，不与某一个智能体绑定。各环境根据自身机制逐步提供适配：

- 独立 Web：由平台进程直接使用内嵌 LadybugDB；
- Cursor：通过其支持的 Skill、插件或 MCP 方式连接；
- ChatGPT/Codex：通过其支持的插件、Skill 或 MCP 方式连接；
- DeepSeek Harness：通过其 Skill 和 MCP 能力连接；
- 其他环境：优先使用 MCP，不支持时使用受控 API。

本地智能体可以按需启动平台的 MCP 接入进程，由该进程在内部打开 LadybugDB，不需要再启动独立数据库服务。Web 或多客户端共同读写时，可由一个平台进程统一持有工作库并协调访问。

## 9. 并发边界

LadybugDB 的嵌入式并发模型要求同一磁盘工作库保持单一受控写入方；多个独立进程可以在只读条件下访问，但不能各自同时打开同一库进行读写。官方建议多客户端读写时由一个应用进程持有数据库并接受请求：[LadybugDB 并发文档](https://docs.ladybugdb.com/concurrency/)。

因此平台需求确定为：普通查询默认只读；蒸馏、安装、评审和发布等写入由平台统一协调；多个智能体共同访问时不能绕过平台直接修改数据库文件。

## 10. 未来容量扩展

平台从一开始按多科目、每科数十本材料和持续新增知识包设计。初期可以使用统一工作库以获得最直接的跨包查询；当真实压测证明单库影响启动、索引、备份或查询时，再按科目或工作空间进行逻辑分区，并由全局目录保存跨科入口和映射。

是否分区、何时分区以及采用何种物理方式留到后续设计阶段决定。当前需求只固定：扩展不能破坏来源边界、热插拔和统一查询体验。

## 11. 后训练模型与热插拔边界

知识包、FormulaSkill 定义和后训练模型是三种不同产物。复制普通知识包只更新可检索医学内容，不自动替换模型；FormulaSkill 版本定义方剂任务能力和数据语义，也不夹带模型权重；模型版本由平台模型注册表单独安装、验证、灰度和回滚。

不同智能体环境可以使用不同大小或不同供应方的基础模型，但必须通过同一能力测试并返回实际模型版本。平台不能因为某个模型已经后训练，就允许它跳过知识包检索、来源引用、统一药物层或医疗安全守门。模型切换后应重新运行方剂、药物层、证据忠实和安全兼容测试。

当前阶段不安装后训练框架，也不把训练依赖加入普通平台发行物。待核心系统跑通并批准《后训练实施与验收方案》后，AI 才能按方案建立隔离、锁定版本且可回滚的训练环境。训练环境与普通知识包运行环境分离，避免让未来可能使用的训练工具扩大当前产品依赖。
