# Agent 平台与任务编排

## 1. Agent 角色

平台最高级执行关系为：

```text
Agent 负责协作和决策
  ↓ 调用
Skill 负责具体能力
  ↓ 受控读写
统一知识包与病例数据模型
```

当前平台基线定义五类逻辑职责：

- OrchestratorAgent：拆分任务、选择当前中医和安全路径、管理状态、失败恢复和最终汇总；
- 数据分析 Agent（原 KnowledgeBuilderAgent 职责）：接收文件并组织格式识别、提取/OCR、知识及病例分析、暂停恢复与数据包构建更新；调用已验收工具，返回任务、数据包和检查结果，不与原角色重复部署；
- TCMReasoningAgent：执行四诊、病机构造、经典方法路由、三层对齐、证候和治法分析；
- EvidenceReviewAgent：检查支持、弱证据、反证、缺失、冲突、证明图、重复、遗漏和医学合理性；
- SafetyGovernanceAgent：检查红旗、急危重风险、权限、隐私、版权、处方和禁忌，并控制高风险阻断与发布治理。

五类职责不是初始部署数量。初始部署使用 OrchestratorAgent 与数据分析 Agent 的最小父子编排；EvidenceReviewAgent、TCMReasoningAgent 和 SafetyGovernanceAgent 只有在对应 Skill、测试与评审条件成立时启用。WesternReasoningAgent 是未来扩展角色，不属于当前路线。

这些角色可以由多个进程、多个模型或同一模型的不同受控任务实现。一个 Agent 可以调用多个 Skill，同一个 Skill 可以被多个 Agent 复用，Agent、Skill、模型和进程不一一对应。新增角色只有出现独立权限、状态、工具、并行吞吐或评价需求时才成立，不能把 Agent 数量当作成果。

## 2. 构建状态机

总智能体下的数据分析 Agent 必须具备产品自身的多格式分析、OCR、暂停续跑与包更新能力。按 [第 16 章](16-PDF资料处理与数据包更新.md)，工具链验收后才接入角色；父子任务身份和进度跨进程持久化，脱离 Codex 仍能运行。地图式问诊阶段依据实际职责补充中医推理、证据评审和安全角色，不预设固定 Agent 数量。

```text
待摄取
  → 已解析
  → 已标准化
  → 已抽取
  → 待构造
  → 待对齐
  → 待复核
  ├─ 可发布 → 已发布 → 已废止
  └─ 隔离区 → 修复后重新复核
```

每次转换记录输入版本、输出版本、执行者、时间、质量指标和失败原因。高风险医学内容不能仅凭模型置信度自动进入“已确认”。

后训练实施时使用独立状态机。当前阶段只保留该治理思路，不表示已经启动训练：

```text
候选反馈
  → 已归因
  → 已脱敏与许可校验
  → 待专家审核
  → 数据集已冻结
  → 训练中
  → 离线评测
  → 专家与安全评审
  ├─ 可灰度 → 灰度中 → 已发布
  └─ 不通过 → 隔离或返工
```

知识包发布和模型发布不得共用一个“已发布”状态。知识包可以更新而不训练模型，模型也只能使用已登记的数据快照训练。

## 3. 任务编排原则

- 确定性处理优先使用程序和规则；
- 语义抽取和候选生成使用模型；
- 高风险结论由专家审核；
- 各 Agent 只获得完成任务所需的最小数据和权限；
- 单个模块失败不阻断无依赖部分；
- 重试有次数限制，失败后进入错误队列；
- 所有写入通过版本化服务，不允许 Agent 直接改正式库。
- 当前中医与安全路径可协作，安全门优先并可阻断后续高风险建议；西医路径留待未来扩展；
- 所有 Agent 共享同一标准病例和证据身份，不各自复制或改写患者事实；
- Skill 必须声明输入、输出、证据要求、失败语义、权限和版本；
- 历史事实、专家结论、规则结果、模型候选和合成反事实分别标识。

## 4. 自动完善闭环

```text
模型候选
  → 自动质检
  → 专家修订
  → 错误类型归因
  → 规则/提示/模型候选改进
  → 独立验证集测试
  → 安全回归测试
  → 新版本灰度发布
```

反馈改善的是抽取器、对齐器或评分器，不应直接把某位用户的修改推广到所有医家和科室。

选择改进手段时遵循由轻到重的顺序：先修复来源或 Schema，再调整确定性规则和检索，再优化提示与工具调用，最后才进入后训练方案设计。只有智能体结构、蒸馏结构和核心链跑通，并能证明问题来自稳定模型行为时，才根据届时项目状态选择具体训练方法。

## 5. 可观测性

平台需要记录任务耗时、Agent 路由、Skill 调用、模型调用、token/费用、失败阶段、重试次数、人工修改量、对齐接受率、安全拦截率和版本差异，支持重现某个知识包或某次病例分析的生成过程。后训练还需记录基础模型、训练数据快照、数据许可、训练方法、随机种子或等价复现实验信息、评测结果、灰度范围和回滚原因。

## 6. LadybugDB 运行边界

LadybugDB 作为嵌入式组件由平台统一管理，普通 Agent 不直接打开、修改或替换数据库文件。所有 Agent 通过平台能力读取数据或提交候选修改，正式写入仍受状态机、质量门和权限控制。

同一工作库需要保持单一受控写入方。查询客户端可以并发读取，但蒸馏、安装、评审发布等写入任务必须由平台协调，避免多个智能体进程同时争用同一数据库文件。独立 Web 和多个智能体需要共同读写时，可以共同连接同一个平台进程；这仍然是平台自身的接入服务，不是额外数据库服务。


## 7. 用户归属与联合使用边界

数据分析 Agent 的多基础包增量学习与联合查询职责见第19章；现有总智能体入口复用，不另造角色。归属不是临床用户/患者身份，也不是查询权限隔离。
