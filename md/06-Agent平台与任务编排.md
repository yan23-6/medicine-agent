# Agent 平台与任务编排

## 1. Agent 角色

- 总控 Agent：拆分任务、管理状态、失败恢复和最终交付；
- 摄取 Agent：登记材料、恢复版面、识别章节和医案边界；
- 证据抽取 Agent：抽取实体、关系、条件、否定、时序和主体；
- 病机构造 Agent：形成病机原子、复合病机和路径候选；
- 三层对齐 Agent：连接基础病机、医家经验和医案实例；
- 质检 Agent：检查证据覆盖、矛盾、重复、遗漏和格式；
- 医学评审 Agent：依据标注指南提出复核建议，不替代专家；
- 训练数据构建 Agent：后训练阶段启用；依据届时已批准方案，从已审核知识和错误样本生成任务样本、执行去重与分组；
- 模型评测 Agent：后训练阶段启用；运行届时冻结的测试、泄漏检查、安全回归和版本对比，不自行放宽发布门槛；
- 发布 Agent：依据统一知识包协议校验结构与自描述、完成版本化并更新索引；
- 运行时病例讨论 Agent：检索相关子图、提出追问并组织回答；
- 安全守门 Agent：检查红旗征象、越权诊断、处方风险和隐私。

这些角色可以由多个进程、多个模型或同一模型的不同受控任务实现。论文重点是职责和评价可分离，不必为了“多 Agent”而增加无效对话。

## 2. 构建状态机

```text
待摄取
  → 已解析
  → 已抽取
  → 待构造
  → 待对齐
  → 待复核
  ├─ 可发布 → 已发布 → 已废止
  └─ 隔离区 → 修复后重新复核
```

每次转换记录输入版本、输出版本、执行者、时间、质量指标和失败原因。高风险医学内容不能仅凭模型置信度自动进入“已确认”。

后训练实施时使用独立状态机。当前阶段只保留该治理思路，不表示已经启动训练：

```text
候选反馈
  → 已归因
  → 已脱敏与许可校验
  → 待专家审核
  → 数据集已冻结
  → 训练中
  → 离线评测
  → 专家与安全评审
  ├─ 可灰度 → 灰度中 → 已发布
  └─ 不通过 → 隔离或返工
```

知识包发布和模型发布不得共用一个“已发布”状态。知识包可以更新而不训练模型，模型也只能使用已登记的数据快照训练。

## 3. 任务编排原则

- 确定性处理优先使用程序和规则；
- 语义抽取和候选生成使用模型；
- 高风险结论由专家审核；
- 各 Agent 只获得完成任务所需的最小数据和权限；
- 单个模块失败不阻断无依赖部分；
- 重试有次数限制，失败后进入错误队列；
- 所有写入通过版本化服务，不允许 Agent 直接改正式库。

## 4. 自动完善闭环

```text
模型候选
  → 自动质检
  → 专家修订
  → 错误类型归因
  → 规则/提示/模型候选改进
  → 独立验证集测试
  → 安全回归测试
  → 新版本灰度发布
```

反馈改善的是抽取器、对齐器或评分器，不应直接把某位用户的修改推广到所有医家和科室。

选择改进手段时遵循由轻到重的顺序：先修复来源或 Schema，再调整确定性规则和检索，再优化提示与工具调用，最后才进入后训练方案设计。只有智能体结构、蒸馏结构和核心链跑通，并能证明问题来自稳定模型行为时，才根据届时项目状态选择具体训练方法。

## 5. 可观测性

平台需要记录任务耗时、模型调用、token/费用、失败阶段、重试次数、人工修改量、对齐接受率、安全拦截率和版本差异，支持重现某个知识包或某次病例分析的生成过程。后训练还需记录基础模型、训练数据快照、数据许可、训练方法、随机种子或等价复现实验信息、评测结果、灰度范围和回滚原因。

## 6. LadybugDB 运行边界

LadybugDB 作为嵌入式组件由平台统一管理，普通 Agent 不直接打开、修改或替换数据库文件。所有 Agent 通过平台能力读取数据或提交候选修改，正式写入仍受状态机、质量门和权限控制。

同一工作库需要保持单一受控写入方。查询客户端可以并发读取，但蒸馏、安装、评审发布等写入任务必须由平台协调，避免多个智能体进程同时争用同一数据库文件。独立 Web 和多个智能体需要共同读写时，可以共同连接同一个平台进程；这仍然是平台自身的接入服务，不是额外数据库服务。
