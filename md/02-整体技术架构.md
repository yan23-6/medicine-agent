# 整体技术架构

平台的最高级业务架构采用“通用医学主干 + 中医专业分支 + 西医专业分支”，最高级执行架构采用“Agent 负责协作和决策、Skill 负责具体能力、统一知识包与病例数据模型负责保存事实和状态”。详细定义见 [14-中西医临床认知与多智能体架构](14-中西医临床认知与多智能体架构.md)。

## 1. 总体分层

平台采用六层结构。后训练属于基础设施与模型治理能力，不另造一套医学知识库：

```text
交互层       Web、管理后台、专家评审台、智能体客户端
接入层       MCP、REST API、SDK、身份认证、限流
运行时层     Agent 编排、Skill 路由、中西医并行推演、上下文、记忆、安全守门
构建层       文件解析、病例标准化、证据抽取、专业机制构造、对齐、质量评审
知识层       统一知识包协议、病例模型、证据库、认知图、状态轨迹、注册表、索引、版本与审计
基础设施层   模型适配、后训练与模型注册、任务调度、文件存储、嵌入式图数据引擎、日志与监控
```

任何客户端都只能通过接入层使用核心能力，不能直接修改知识数据库。

## 2. 通用主干和专业分支

通用主干固定原始材料、来源证据、标准病例、诊次时间线、观察、假设、冲突、综合状态、目标、干预、状态变化、结果、质量和安全对象。中医分支增加四诊、病机、证候、治法、方剂、药物、针灸和传变；西医分支增加标准表型、危险因素、病理生理、检查、诊断、鉴别、风险、干预和预后。

两条分支共同引用通用病例和证据对象，不复制患者事实。安全分诊与两条专业路径并行，并可在高风险状态下阻断后续建议。中医与西医结果可以围绕共同观察、时间和结局建立受控关联，但不相互改写概念定义。

## 3. 核心平台与适配器

核心平台保存全部稳定能力：知识包管理、三层对齐、病例支持度、检索、评审、权限和审计。外部环境只保留安装清单、Skill 指令和连接配置。

项目级统一知识包协议属于核心平台的稳定契约。所有蒸馏器、数据包、适配器和运行库共同遵守它；单个数据包只声明自身身份、协议版本、资料配置、来源范围、质量与许可等差异信息，不能自定义另一套解释规则。

因此，一次平台发布可以生成多个产物，但它们共享同一核心：

```text
核心服务 ── Web 应用
       ├── MCP Server
       ├── REST API / SDK
       ├── Agent Plugin
       ├── Cursor 适配包
       ├── ChatGPT/Codex 适配包
       └── DeepSeek Harness 适配包
```

## 4. 默认图数据引擎决策

平台默认采用 LadybugDB 作为嵌入式图数据引擎。选择理由是：

- 它以库的方式嵌入平台进程，不需要用户另行安装或启动数据库服务；
- 支持磁盘持久化、属性图和 Cypher，适合保存与查询病机节点、来源关系和动态路径；
- 支持全文与向量检索能力，符合原文证据检索和语义召回需求；
- 可以随不同操作系统的发行物一起提供，符合解压或安装后即可使用的产品目标；
- 与过去采用 Kuzu 的嵌入式思路接近，迁移和认知成本相对较低，而 Kuzu 原项目已停止维护。

LadybugDB 官方说明其为无需独立服务器的嵌入式数据库，并支持磁盘数据库、事务和属性图：[LadybugDB 入门文档](https://docs.ladybugdb.com/get-started/)。全文与向量能力分别见[全文检索文档](https://docs.ladybugdb.com/extensions/full-text-search/)和[向量检索文档](https://docs.ladybugdb.com/extensions/vector/)。

LadybugDB 是当前默认选型，不意味着平台业务语义与其专有实现绑定。若未来超大规模或机构部署确需外部数据库，可增加其他存储适配方式，但不能给默认安装增加外部数据库依赖。

## 5. 存储边界

LadybugDB 保存可查询的知识节点、关系、专业机制路径、标准病例、诊次状态、临床认知图、状态轨迹、原文证据文本、来源定位、知识包身份、版本和审核状态。大型原始 PDF、页面图片及其他二进制材料可以由平台文件存储管理，图数据中保留身份、位置和校验关联。

原文不重复堆放在每一个病机节点内，而作为可独立引用的证据对象保存；一个病机节点、关系或病例判断可以共同引用同一证据。这样既保留完整原文依据，又避免跨包和跨节点重复复制。

当前阶段只固定上述逻辑边界，不确定具体节点表、关系表、字段类型、目录结构和分片阈值。

## 6. 数据流

```text
源文件
  → 解析/OCR/分段
  → 唯一证据层
  → 知识节点与来源推理片段/标准病例
  → 通用临床认知对象
  → 中医病机路径与西医临床路径候选
  → 三层对齐/专业对齐/安全门
  → 自动质检与人工复核
  → 按统一知识包协议封装、校验与发布
  → 运行时检索与病例辅助推演
  → 评审反馈
  → 错误归因与后训练资产候选
  → 新版知识包、Skill 或规则构建
  → 在智能体与蒸馏结构跑通后触发后训练方案设计
  → 按批准方案执行训练、评测、灰度与回滚
```

下游必须记录上游版本。任何修订都通过新版本或修订记录完成，不能静默覆盖。

## 7. Agent、Skill、模型与存储解耦

```text
Agent 负责协作和决策
  → 调用 Skill
Skill 负责具体能力
  → 通过平台受控访问统一知识包与病例数据模型
```

Agent 是逻辑职责，不等同于模型或进程；Skill 是可复用能力，不等同于医学事实或独立智能体。Skill 基础未稳定前不实现多 Agent；MVP 先使用编排、知识构建和证据评审三个逻辑 Agent，随后仅在对应 Skill、权限、状态、专门工具、并行吞吐或独立评价条件成立时启用中医、西医和安全治理角色。

平台通过统一能力边界调用不同大模型，覆盖结构化抽取、候选对齐、路径生成、一致性复核和对话表达。知识、评审结果和版本状态不依附于某个模型。业务层也不应直接依赖 LadybugDB 的文件细节；更换模型或增加存储适配方式时，不能改变原始证据和已确认断言的语义。

后训练模型与知识包分别版本化。当前阶段先保证运行结果能够保存基础模型、知识包集合、检索配置、Skill、提示、规则和安全策略版本，为未来冻结项目快照提供依据。后训练实施后，模型版本还需记录训练方法、训练数据快照、代码与超参数、评测结果和适用任务。

方剂能力采用“一个 FormulaSkill 对应一个组合式能力图”的逻辑边界。FormulaSkill 内部包含方剂识别、病机解释、统一药物层、加减、状态转移、停调、选择和比较等能力。药物层一次接收整方药物集合，并引用可复用的单味药基础知识；它不能把每味药当作互不关联的顶层 Skill，因为剂量、炮制、配伍角色和协同制约只有在具体方剂上下文中才成立。
