# 知识蒸馏 Skill 与构建流水线

## 1. Skill 定位

知识蒸馏相关 Skill 是可注册、可调用、可版本化和可测试的软件能力，负责判断材料类型、执行或调用抽取策略、产生结构化候选并返回证据、错误和质量信息。Skill 不承载全部医学内容，也不直接充当数据库或正式发布服务。

Skill 与 Agent 分层：Agent 负责任务协作、路径选择、状态管理和结果决策，Skill 负责可复用、可测试的具体能力，二者通过统一知识包和病例数据模型交换信息。一个 Agent 可以调用多个 Skill，同一 Skill 可以被多个 Agent 复用。

平台基线定义十一类 Skill 家族：

- MaterialIngestionSkill；
- EvidenceGroundingSkill；
- KnowledgeDistillationSkill；
- CaseDistillationSkill；
- TCMReasoningSkill；
- WesternReasoningSkill；
- SafetyGateSkill；
- FormulaSkill；
- KnowledgePackageBuildValidateSkill；
- KnowledgePackageQuerySkill；
- QualityEvaluationSkill。

它们是顶层能力家族，不要求每个解析步骤、规则或模型提示都发布为独立 Skill。详细成立条件、调用协议和启用顺序见 [15-Skill运行规范与知识包生产消费闭环](15-Skill运行规范与知识包生产消费闭环.md)。

单独的 `SKILL.md` 或提示词只提供说明，不能证明 Skill 已实现。可调用 Skill 还必须具备机器 Schema、执行入口、实现、错误语义、证据约束、测试夹具和验收结果。

这里的“可组合 Skill”是平台工作流模块。对于具体方剂，对外发布的是一个组合式 FormulaSkill，不把八项能力或每味药分别做成需要独立安装和维护的顶层 Skill。FormulaSkill 内部统一包含：方剂识别、病机解释、药物层、加减、状态转移、停调、方剂选择和方剂比较。

药物层采用一主多单元结构：一个 DrugLayerSkill 管理当前方剂的全部药物单元和配伍关系；每味药引用可复用的 HerbKnowledge，并另存当前方剂中的 FormulaHerbRole。这样既能复用单味药知识，也不会丢失整方配伍语境。

## 2. 材料识别

平台首个正式蒸馏版本目标支持 PDF、DOCX、Markdown 和 TXT。阶段 01 的协议闭环只要求 Markdown 或 TXT 测试夹具；PDF、DOCX、表格和图片只有在相应解析能力实现并通过测试后才能标记为支持。同一文件内部按片段识别：

- 教材/专著：概念、分类、机制、辨析和方法；
- 名医经验：主张、辨证抓手、用药特点、条件和禁忌；
- 医案：诊次、四诊、病机、治法、处方和转归；
- 论文：问题、样本、方法、结果、证据与局限；
- 表格/图片：逐项转录、结构恢复、位置和识别质量。

不能因为文件总体属于“书籍”，就对所有章节使用同一个模板。

## 3. 构建流程

本流程只有在所需 Skill 已实现并通过注册、契约和测试验收后才能运行。不存在相应 Skill 时，平台必须返回能力缺失，不允许模型临时模拟成功结果。

1. 登记材料、计算指纹、记录版权与隐私状态；
2. 解析版面、OCR、恢复章节、识别表格和图片；
3. 分类文档片段，识别医案及诊次边界；
4. 对病例执行 `RawCase → CanonicalCase`，分别保存原始值、纠正候选、诊次时间线和文本不确定项；
5. 抽取医学实体、属性、观察、否定、条件、时间和陈述主体；
6. 抽取知识关系、来源推理片段、支持、弱证据、反证和缺失信息；
7. 形成基础知识包，使其可以独立检索和即时推演；
8. 按通用临床认知链构造多假设、专业机制、冲突、综合状态、目标、算子、行动和状态变化候选；
9. 分别进入中医病机路径、西医临床路径和安全门；中医路径继续构造病机原子、复合病机、动态路径和三层对齐；
10. 执行规则校验、模型复核、证明图检查和跨片段一致性检查；
11. 将低置信、高风险、冲突和无法核实内容送入人工复核；
12. 按统一知识包协议生成多视图、包自描述、质量报告和错误清单；不为单包重复生成说明书；
13. 原子化发布、更新索引并记录完整版本。

若材料包含方剂，构建流程还要生成组合式 FormulaSkill 候选：先抽取方剂组成、剂量、炮制和用法，再把全部药物放入同一药物层，形成方中角色、配伍关系、加减条件、状态变化和停调规则。任何原文未说明的方义、药物角色或状态转移均标为模型候选，不能伪装成来源事实。

发布后的知识包保持独立可交换，不直接等同于 LadybugDB 数据库文件。平台在安装知识包时负责把已通过校验的内容纳入嵌入式工作库；因此不同人员蒸馏的兼容数据包可以共同使用，而不要求制作者共享同一个数据库实例。

正式蒸馏前必须先用测试材料通过以下闭环：材料摄取与证据定位 → 最小知识对象 → 知识包构建与校验 → 知识包查询 → 来源回溯。只生成包而没有校验和查询，不得认定数据可用。

## 4. 医学专项检查

- 不混淆病因、病机、证候、证型和病名；
- 不把症状出现视为病机必然成立；
- 识别可见、常见、多见、必见、未见等强度差异；
- 识别否定、假设、比较、鉴别和引用他人观点；
- 区分医家原按、编者按和系统分析；
- 不把不同诊次拼接成同一病理状态；
- 提取主次、标本、缓急、兼夹和动态转化；
- 处方反推病机只作为候选；
- 治疗后好转不单独证明病机正确。
- 不把历史诊断和历史治疗改写为当前确认结论；
- 不从单一特征直接跳到证型、诊断、方药或穴位；
- 不把中医病机与西医病理生理强行等同；
- 不把专家软标签和模型分数表述为真实临床概率；
- 不把反事实、预测状态或证明图中的模型候选回写为病例事实；
- 高风险病例必须先完成安全门，不能因中医或历史路径完整而跳过。

## 5. 断点与可重建性

每一步均可单独重跑，并保存输入输出版本。任务状态包括未处理、处理中、成功、失败、跳过和待复核。源文件变化后不能直接沿用旧断点。重复运行不得无控制地产生重复节点，未完成批次不能破坏已发布版本。

## 6. Skill 的自我完善

专家修改首先被记录为结构化错误样本，并归因到 OCR、实体、关系、对齐、路径或安全模块。只有改进方案在独立验证集上提升且不降低安全指标，才发布新的 Skill、规则或模型配置。普通对话和未经审核的病例不能直接成为正式规则。

“自我完善”不等于系统在线自动训练。反馈首先进入隔离的候选池，经去标识化、许可检查、错误归因、重复检查和专家审核后，才可进入下一轮规则修改、提示优化或后训练数据。知识包更新、Skill 版本更新和模型后训练分别发布，不能用一次模型训练掩盖数据错误或协议缺陷。

## 7. 数据包发布与安装要求

蒸馏 Skill 交付的数据包必须能够被平台独立识别，至少声明材料身份、科目、内容类型、版本、兼容要求、处理范围、质量状态和完整性校验信息。

蒸馏 Skill 的输出必须符合项目唯一的知识包协议说明书。教材、论文、医家经验和医案使用同一核心结构，只通过资料类型配置启用不同的可选内容与质量规则。发布流程校验的是“数据是否符合统一协议”，而不是为新包创造新的解释方法。

安装过程由平台自动完成：发现数据包、校验、暂存、纳入 LadybugDB 工作库、更新全文与向量检索、生成跨包候选映射，最后切换为可用状态。任何一步失败时保持旧的可用状态，并把新包放入隔离或待处理状态。

安装自动化不等于忽略处理时间。大包首次纳入和建立索引可能耗时，平台必须显示进度，完成前不能把未就绪内容伪装为可查询。

## 8. 后训练数据构建流水线

当前构建流水线不直接生成并启动正式训练，只保存未来需要的证据引用、结构化结果、专家修订、错误类型、实际调用版本、许可与风险状态。整本书、全部医案和普通对话不能未经审核直接作为训练数据。

等智能体结构、蒸馏结构和核心链实际跑通后，项目冻结当时的 Schema、任务接口、错误分布和评测基线，再设计与真实结构一致的训练数据构建流水线。届时才确定样本格式、纳入规则、去重与划分、审核比例、训练方法、验收阈值和执行工具。

后训练启动条件及未来方案要求见 [13-方剂药物层与后训练方案](13-方剂药物层与后训练方案.md)。

未来可从同一证据和病例对象重建病例标准化、表型规范化、安全分诊、中西医机制推断、冲突分析、目标规划、工具调用、状态预测、错误负样本、偏好对和反事实等任务视图。不同视图分别确定用途，不统一贴上“预训练数据”标签；历史事实、专家标注、模型候选和合成样本必须保持来源隔离。
