# 中西医知识蒸馏与智能体平台：设计文档总览

> 状态：方案基线 v1.7
> 固化日期：2026-09-24
> 平台主线：通用医学主干—中医与西医专业分支—病例诊疗状态轨迹
> 当前研究主线：中医病机
> 中医核心结构：通用病机分类—名医病机经验—医案个体病机
> 技术原则：一次证据抽取、多视图生成；图存储、树展示、链推演；Agent 与 Skill 分层；方剂 Skill 组合化、药物层统一管理；检索与后训练分工；LadybugDB 嵌入式运行；核心平台独立运行、多环境薄适配

## 项目定义

本项目建设一套可独立运行的中西医知识蒸馏与临床推理支持平台。平台先建立来源、证据、病例、时间、评审、安全和版本等通用主干，再分别接入中医和西医不可互相替代的专业方法与知识。中医当前以病机为研究主线，构造通用病机、名医经验、个体医案三层可审计结构；西医按病史、危险因素、病理生理、检查、诊断、鉴别、干预和预后组织。两条路径可以围绕同一病例并行，但不得强行合并理论概念。

平台同时把无序材料和医案转化为规范化知识、证据化临床认知图和多诊次状态轨迹，并通过 Web、MCP、REST API 和环境适配包供智能体调用。最高层执行原则是：Agent 负责协作和决策，Skill 负责具体能力，统一知识包与病例数据模型负责保存事实和过程状态。

平台用于中西医知识研究、教学、病例整理和医生辅助，不替代执业医师，不直接面向患者作出确诊或开具具体处方。

## 已固定的核心决策

1. 通用医学主干是平台知识与病例过程的共同基础；中医当前以病机为研究主线，并连接病因、病位、病性、证候、四诊、治法、方药及转归。
2. 所有蒸馏产物遵守同一套项目级“统一知识包协议说明书”；每份材料形成一个可独立使用的数据包，包内保存知识节点、来源推理片段、原文证据和最小机器自描述，但不重复附带独立说明书。
3. 不为不同用途建立相互独立的事实副本；基于唯一证据层和统一病例事实生成知识、推理、中医、西医、病例轨迹和任务样本等受控视图。
4. 病机专题蒸馏负责把已有知识与推理片段连接为完整路径；没有预构建路径时，知识包仍可用于即时推演。
5. 病例提高的是特定条件下某条路径的经验支持度，不直接证明医学正确性。
6. 三层结构底层采用图，面向用户显示为树，面向病例分析展开为链。
7. Agent 负责流程协作、路径路由和受控决策，Skill 负责具体能力与质量检查，医学内容存放在独立、可版本化、可热插拔的知识包和统一病例模型中。
8. 核心平台必须脱离任何智能体独立运行；Cursor、ChatGPT/Codex、DeepSeek Harness 等只使用薄适配层。
9. MCP 是智能体接入的主要公共接口，REST API 与 SDK 是程序接入和兼容兜底。
10. 医疗安全策略独立于角色提示词，并具有更高执行优先级。
11. 默认图数据引擎确定为 LadybugDB，作为应用内部组件运行，不要求用户安装或维护独立数据库、Docker 或额外数据库服务。
12. 知识数据包与运行数据库分离：数据包是可复制、可校验的交换产物；平台发现数据包后，将其纳入统一的 LadybugDB 工作库和联合索引。
13. 同一科目的教材、论文、名医经验和医案包可以同时启用、共同查询，但所有来源节点和版本边界必须保留。
14. 多环境支持通过不同的轻量适配方式逐步实现；LadybugDB 和必要检索扩展应随对应平台发行物一起提供，尽量避免运行时额外下载依赖。
15. 教材、论文、名医经验和医案不是四套数据结构，而是统一结构下的资料类型配置；统一核心对象保持一致，不适用部分允许为空，可按资料类型增加受控扩展。
16. “复制即用”的前提是数据包声明的协议版本兼容且通过完整性、安全和许可校验；新增普通数据包不新增说明书，只有统一结构语义变化时才升级项目级说明书。
17. 总体需求仍按阶段评审，当前已进入 T01 Skill 基础设施建设；T01 可以固定参考实现的代码目录、实验 Schema 和接口字段，但数据库表、正式知识包 v0 和后续阶段算法仍在对应阶段评审后确定。
18. 一个方剂只发布一个组合式 FormulaSkill；方剂识别、病机解释、药物层、加减、状态转移、停调、方剂选择和方剂比较是其内部能力，不按每味药拆成可独立安装的顶层 Skill。
19. 药物层采用“一个药物层 Skill 管理多味药物单元”的结构。单味药的固有属性可复用，剂量、炮制、配伍角色、协同制约和条件加减必须绑定具体方剂、来源和适用状态。
20. 后训练不承担医学事实存储。知识包和检索负责提供可更新、可追溯的医学事实，后训练负责教会模型稳定执行结构化任务、遵守证据边界、使用工具并满足安全约束。
21. 后训练作为项目后续正式阶段预留。当前只持续保存证据、专家修订、错误类型和可复现基线；待智能体结构、蒸馏结构和核心链端到端跑通后，依据届时项目快照另行固化具体训练、安装和验收方案，审批通过后才执行。
22. 平台内的蒸馏、病例标准化、中医、西医、方剂、药物、评审和安全 Skill 共同服务“材料与病例—证据—多假设与专业机制—冲突与安全—目标与行动—状态变化—随访再评估”的核心链，不建设互不关联的 Skill 集合。
23. 平台采用“通用医学主干 + 中医专业分支 + 西医专业分支”。两条专业路径共享证据、病例、时间、干预、结局、安全和治理对象，但分别保存中医病机与西医病理生理、诊断和指南语义。
24. Agent、Skill 和数据层严格分工：Agent 负责任务协作、路径选择与决策；Skill 提供可复用、可测试的具体能力；统一知识包与病例数据模型保存可追溯事实和状态。三者不一一对应。
25. 平台基线定义六类 Agent 职责，但不要求同时部署。Skill 基础稳定后，MVP 先启用编排、知识构建和证据评审三个逻辑 Agent；中医、西医和安全治理角色在对应能力通过验收后启用。仅在权限、状态、并行、工具或独立评价确有需要时继续拆分。
26. 医案必须先从原始文本构造标准病例，再进入中西医推演。OCR 原值、纠正候选、历史诊断、历史治疗、平台推断和现代建议分别保存，不能互相覆盖。
27. 通用临床认知链固定为“观察—标准特征—多假设—专业机制—冲突与缺失—综合状态—目标—算子—行动—状态变化—响应”。它是可审计对象链，不是要求输出模型隐藏思维过程。
28. 中医、西医和安全路径可以并行运行；安全门优先于专业角色、历史医案和治疗推演。高风险状态未排除时，系统阻断或降级相关诊疗建议。
29. 治疗设计遵守“机制与状态—目标—治疗算子—具体干预—状态变化”，禁止从病名或证型直接机械映射方药、穴位或西医处置。
30. 一个病例可以生成标准化、表型、机制、冲突、目标、工具调用、状态预测、负样本和反事实等多种可重建任务视图；正式训练用途在核心链跑通后另行审批，不能笼统视为已获准的预训练数据。
31. Skill 只有在身份、版本、机器 Schema、调用入口、实现、错误语义、证据约束和自动测试同时存在时才算已实现；单独的提示词或 `SKILL.md` 不是可调用能力。
32. 平台基线定义十一类核心 Skill 家族：材料摄取、证据定位、知识蒸馏、病例蒸馏、中医推理、西医推理、安全门、方剂、知识包构建校验、知识包查询和质量评价。
33. 正式蒸馏开始前，必须先通过“生产 Skill—知识包构建与校验—查询 Skill—来源回溯”的最小闭环。测试材料可用于开发，但未通过闭环的输出不能标记为正式知识包。
34. 项目任务由 `tasks` 中的状态和阶段门驱动。任何 AI 必须读取当前真实能力，不能把设计目标或未来阶段草案当作已存在能力。
35. 来源字段缺失时保留字段并使用 `null`；不同 key 同义、同 key 异义、重复 key 和无法映射字段都必须保存原始观察和映射状态，不能为满足 Schema 而丢弃数据。规范字段语义和映射规则由项目级统一知识包说明书管理。

## 阅读顺序

首次了解项目时先读本页、第 14 章、第 15 章和 `tasks/STATE.md`，再按编号阅读其他专题。开发单个模块时，还必须读取当前阶段任务；任何局部设计不得违反本页“已固定的核心决策”。如确需改变核心决策，应先修改本页、记录原因和版本，再同步修改受影响文档与未来任务草案。

关于蒸馏后数据包结构和项目级“说明书”的规范性定义，以 [04-知识包与证据数据模型](04-知识包与证据数据模型.md) 为唯一主文档；其他文件只描述该协议在各模块中的使用方式，不另行定义竞争版本。
